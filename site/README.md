# RooAGI Skills Atlas

A responsive React catalog for canonical `SKILL.md` files under `rooagi/` and `vendor/`, plus every skill below configured roots in pinned Anthropic, AWS Agent Toolkit, Cloudflare, and Alireza Rezvani upstream submodules. It searches names, descriptions, and the complete instruction text; each entry has rendered Markdown details, source attribution, and license metadata.

## Run locally

Requirements: Node.js 20.19+.

    cd site
    npm install
    npm run dev

The development server generates `public/catalog.json` from canonical skill files and all configured submodule catalog roots before starting. Build with `npm run build`. The local Node server binds to 127.0.0.1:4173 by default. Set PORT and HOST to change the listener. The optional Membrick server adapter uses `MEMBRICK_PROJECT_ROOT` to select the skills checkout and `MEMBRICK_PROVIDER` to choose the connected agent provider (defaults to codex).

## Curation and catalog data

The generator reads canonical `rooagi/**/SKILL.md` and `vendor/**/SKILL.md` files and every `SKILL.md` beneath the configured `catalogRoot` of each pinned submodule. Alireza Rezvani / claude-skills uses the full repository root (`.`), including `finance/skills/finance-skills/SKILL.md`; non-SKILL documents are not catalog entries. Catalog roots bound discovery to registered repositories. For Anthropic, AWS Agent Toolkit, and Cloudflare, skills are read directly from submodules and are not copied to `vendor/`. Per-skill license files are included when present; otherwise the catalog records available root license text, upstream notices, repository, path, pinned commit, attribution, and license status. A missing per-skill license file does not exclude a skill. Distinct paths are preserved even when file contents are duplicates, and generation reports raw candidates, included entries, and duplicate copies per source and total. The catalog artifact at `site/public/catalog.json` is regenerated by `npm run catalog` and during dev/build. Do not edit the generated file by hand.

The source trees live in Git submodules pinned by gitlinks (`upstream/claude-skills`, `upstream/anthropic-skills`, `upstream/aws-agent-toolkit`, and `upstream/cloudflare-skills`). To advance a pin, fetch and inspect a proposed upstream commit, verify source and license metadata, then update that submodule to the full commit SHA in a dedicated branch. The `skills` lists in `sources.json` define paths that sync validates; `catalogRoot` independently defines the bounded catalog scan. The catalog includes every skill below each configured root, even when a per-skill license file is absent. Cloudflare's root `skills/` excludes plugin metadata, rules, and MCP configuration outside that root. Review the gitlink diff, generated catalog diff, and upstream changes between the old and new commits; run sync validation and the site build; then submit a PR. Merge only after review. The scheduled vendor sync workflow does not advance submodule pins.

To add or remove a vendored skill, edit selected paths/exclusions and the pinned source commit in root `sources.json`, then run `node scripts/sync.mjs`, review the source/license metadata and diff, and commit the canonical config/content changes. For Anthropic, edit the explicit sync paths only after verifying each path's `LICENSE.txt` at the gitlink commit; catalog discovery remains independent and includes every skill beneath its root. For RooAGI-owned skills, add/remove `rooagi/<skill>/SKILL.md`. The next catalog generation picks it up. Never edit generated `vendor/` files directly.

The Vercel candidates `vercel-react-best-practices` and `vercel-react-native-skills` from the research post were not imported: the post verified MIT declarations at mutable `main` URLs but did not establish license terms and content at an exact pinned revision. Add them only after pinning and reviewing that revision through `sources.json` and the normal sync/PR path.

## Search architecture and limits

The generated static catalog is the source for browsing, immediate local full-text search, and skill detail content. As a visitor types, the site searches catalog names, descriptions, sources, and complete instructions in the browser; submitting the form does not make a network search request. This works on GitHub Pages without a Membrick backend. The optional Node server adapter at `/api/skills/search` can still provide Membrick-ranked results to other server-side integrations, but the site client does not call it. The adapter maps Membrick paths to exact entries in the generated catalog, so only curated skills can appear and result paths never trigger arbitrary workspace file reads.

The Node API uses the official Membrick package server-side. Set `MEMBRICK_PROJECT_ROOT` to the skills checkout and `MEMBRICK_PROVIDER` to the connected agent provider (defaults to `codex`) when running the optional adapter. Keep the resident, index, workspace path, and provider credentials on a trusted Node host. **GitHub Pages serves static files only**: it cannot run `site/server/index.mjs` or `site/server/api.mjs`, and no Membrick credentials or index are shipped to the browser. Search on Pages and in the site client always uses the local catalog. A separately built integration may call the Node endpoint through a same-origin proxy; a public API also needs access controls, CORS, rate limits, and monitoring.

## GitHub Pages deployment

`.github/workflows/deploy-site.yml` builds and publishes `site/dist` on pushes to `main` and manual workflow dispatch. Project Pages uses the `/skills/` Vite base. Hash-based detail navigation works on static hosting.

Repository setup:

1. In **Settings → Pages**, select **GitHub Actions** as the source.
2. No deployment secret is required. The workflow uses built-in `GITHUB_TOKEN` with `pages: write` and `id-token: write`, and the official Pages artifact/deploy actions.
3. Pages is static and has no Membrick runtime or server environment variables; the local catalog provides search without a separate API.

The first deployment requires this workflow to be merged/run and Pages to be enabled. GitHub Pages may take a few minutes to publish initially. Roll back by reverting the source commit and letting Actions publish it again.
